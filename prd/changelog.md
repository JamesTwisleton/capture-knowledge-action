## Changelog

- **v0.9.6** — Shipped the **Apache License 2.0** `LICENSE` file, with a License section in the README and Section 13 updated to match. Pulled forward out of T20: the repository is public and calls itself open source in the README and on the landing page, so until now readers had no actual grant of rights. The file is the canonical text, unmodified (`md5 3b83ef96387f14655fc854ddc3c6bd57`). Also added MCP compatibility as a product-level claim and a build ticket. CKA defines an **MCP compatibility spec** (`docs/mcp-spec.md`), published in the repo and covering the whole stack: CKA's own core capabilities — triage, the action decision chain, stored knowledge, provider health, error recovery — and every provider interface, so a provider can be satisfied by any MCP-conformant server rather than bespoke CKA code. It is a specification any component can implement independently, not a single centralised server. The load-bearing architectural point: **a deterministic REST/JSON API stays the core, and MCP is a thin layer wrapping it** — the application services are designed, built and tested as an API in their own right, and the MCP reference implementation calls straight through to them afterwards; MCP is the intended day-to-day entry point for AI agents, which is a usage goal rather than a claim about which layer drives the other's design. Tool names, descriptions and schemas are held to a **discoverability bar**: a generic MCP client with no CKA-specific knowledge must map a plain natural-language request onto the right tool calls from the exposed schema alone. New Section 3 bullet, new 8.1 bullet, new Section 10 extension point, two known-limitation rows, three open questions, and decision log entries 57–58. The ticket breakdown gains **T18 (MCP compatibility)**, inserted after T17 so it wraps the finished API, pushing test data, setup scripts and the demo to T19, T20 and T21 — 21 tickets now, with the GitHub epic and sub-issues renumbered to match.
- **v0.9.5** — Closed the last direct call in the pipeline. The LLM provider no longer hands its output to the knowledge provider: it publishes a **content-summarised** event, the knowledge provider subscribes to it and performs the write, and it is that write completing which fires the existing knowledge-stored event. Every handoff in the pipeline now crosses the event bus, so any provider can be built, tested and swapped without the next one — J1's steps and sequence diagram, the stages diagram in 7.1, the provider table rows for LLM and Knowledge, the event list in 8.1, and T06/T07/T12 all redrawn around it. The event is named for summarising rather than transcribing, since decision 40 removed transcription from the MVP entirely. Mention detection gains a third outcome: a mention scoring below the threshold is now a **proposed comment** in the Triage Inbox rather than being dropped, so the Inbox holds two distinguishable kinds of proposal and check 1 in the gate model branches three ways — auto-comment, propose, or record as an unmatched mention. "Trigger phrase" is fixed as the canonical term over the competing "wake word" and "wake phrase". New [`prd/demo-script.md`](demo-script.md): the demo script narrated on 19 September 2026, structured for delivery and doubling as the MVP test plan (T21, renumbered from T20 later in v0.9.6), with a beat checklist and a record of every correction made to the narrated version — including the reject path and the reset, which the narration had not covered at all. Decision log entries 52–56 added; Section 14 and the ticket breakdown updated to point at the script.
- **v0.9.4** — Scoped and specified the MVP: a real, local, dockerised end-to-end slice (Google Meet recording → Markdown vault → GitHub Issues) with a terminal setup wizard and a scripted demo recording, filed as GitHub epic [#1](https://github.com/JamesTwisleton/capture-knowledge-action/issues/1) with 20 sub-issues and written up in the new [`prd/mvp-tickets.md`](mvp-tickets.md). Knowledge and Action are now decoupled by a "knowledge stored" event, which J1's steps and sequence diagram were redrawn around: the Action stage starts from the event rather than being called directly. Mention detection becomes the decision provider's job alone, working from the summarised knowledge content against the real candidate pool — the LLM step never extracts ticket identifiers, and a reference matching no real candidate becomes a recorded **unmatched mention** rather than a silent drop. Prompts move from configuration to versioned SQL data keyed by content type, with front-end editing in the MVP; migrations use Flyway and data access Spring Data JDBC. The decision provider gains an LLM fallback for anyone without a Jev key, and Jev is noted as early access. Folder capture is by polling; RabbitMQ is the MVP's event bus broker; the GitHub candidate pool is unfiltered for the MVP. Triage accept is stated as the final approval with no second dialog, and accept-all is added. Trust-ramp suggestions and full Outbox behaviour (retry, switch provider, dismiss) are in the MVP; audio transcription and notification delivery are not. New 7.9 covers the work item model — work item mapper, nested work items, provider work item type name — and Section 10 names the mapper and the connection/health check as extension points, alongside the repo conventions for contributors and coding agents. Gates are renamed **action checks** against **action thresholds**, and the full record is the **action decision chain**, with prompt version now an audited field. The single-persistent-core (not serverless) rationale answers a reviewer's serverless suggestion. Licence confirmed as Apache License 2.0 and the public demo host as GCP, closing two open questions along with the demo's provider combination and MVP OAuth handling; a secrets provider beyond `.env` stays open. The data-sensitivity warning now names the decision provider, which also receives transcript segments. Decision log entries 27–51 added, entries 3, 5 and 21 amended, and known limitations, open questions and next steps updated throughout.
