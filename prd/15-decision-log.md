## 15. Decision log

How we got here, in order. Each entry records the decision and the reasoning at the time so the trail is reviewable later.

1. **Start from the observed pattern, not a blank page.** Organisations are repeatedly building the same meeting → summariser → knowledge store → work tracker pipeline, each one bespoke and fully vendor-coupled. Decision: build an open-source, provider-agnostic framework rather than another bespoke pipeline, because lock-in is the actual problem.
2. **Check for prior art before designing.** Meetily and anarlog were found: strong on swappable LLMs and local-first transcription; platform integrations (Confluence, Jira) thin or planned. Decision: proceed; the gap is swappable platform providers plus onboarding. A standing rule was set to re-check at every stage.
3. **Integrate Jev as a decision layer, not a summariser.** Jev returns constrained decisions with calibrated confidence rather than prose. Decision: use it for mention detection over a candidate pool and for classifying trigger-phrase actions. Motivation is both fit and a deliberate opportunity to exercise a new class of model. *Amended (v0.9.4):* Jev is optional, with an LLM-based fallback behind the same interface for anyone without a TypeSafe key, and the Jev adapter is a thin wrapper written in this codebase calling the HTTP API directly, since no official Java SDK exists — see entries 33 and 60.
4. **Name provider categories by capability, not vendor.** "Knowledge provider", not "Confluence provider". Decision: the wizard asks "which implementation for each capability", vendor names never enter the domain model.
5. **Java Spring Boot backend, Next.js front end.** The backend does the processing and needs to scale in large organisations. Spring's dependency injection (DI — the mechanism that hands the core whichever implementation of an interface is configured) fits the provider pattern naturally. A separate configuration UI makes setup easy, and answers the "why not something lighter than Java?" objection: the heavy lifting is Java, the experience is a web app. *Amended (v0.9.4):* the core is one persistent application, not serverless functions — see entry 27.
6. **Cloud-agnostic by design; one tested path.** Terraform per cloud in the repo; only one deploy path built and tested in v1, others clearly marked untested.
7. **Scope the candidate pool before Jev.** A fixed-choice classifier cannot sensibly choose among tens of thousands of tickets. Decision: pre-filter by board, recency and status, all configurable. The tool's limits shaped the architecture.
8. **Trigger phrase for mutating actions; comments need none.** Passive mentions always get the low-risk action; anything that changes state requires the team wake word. Two-gate model, with Jev confidence on top.
9. **Human review first; trust per action type.** All mutating actions start in a Triage Inbox. Accuracy is measured against human decisions; the system offers auto-approve when it earns it and offers disable-or-switch-provider when it doesn't. Trust is per action type with sensible defaults. Audit trail is mandatory to make this trustworthy.
10. **Failures become a queue, not a silent stall.** Outbox plus notification, with retry, switch provider, or dismiss.
11. **Don't build an LLM gateway.** LiteLLM and LangChain4j were found to fully cover provider-agnostic access, routing and per-call cost tracking. Decision: consume one of them; CKA's unique contribution is the workflow orchestration, platform providers and safe action layer. Local models come free as a result.
12. **"Work item provider", not "ticketing provider".** "Ticket" is Jira-flavoured language; "work item" covers Jira, Azure DevOps Boards, GitHub Issues and Linear equally.
13. **Three composable stages, event-driven.** Meetings are not required (J3) and actions are not required (J2). Decision: Capture, Knowledge and Action as independently invokable stages connected by events; the event bus is itself a provider with a deliberately simple interface (Kafka, Pub/Sub, RabbitMQ).
14. **Dedicated audit service on SQL, optional but frictionless.** Pluggable SQL provider with SQLite bundled by default; if absent, functionality degrades with a clear call to action.
15. **Ambiguity is pushed back to the user.** Garbled wake words are a documented known issue with guidance. A "close it" with no item ID is ignored rather than guessed: the ID must be spoken. The system is deliberately conservative.
16. **Same-vendor bonuses are surfaced, not hidden.** Core functionality is agnostic; the wizard tells you when a pairing has extra integration available.
17. **Costs: predicted and actual.** Live prediction for the "should I switch?" decision, reconciled against linked provider billing so the estimate's accuracy is visible.
18. **Name: Capture-Knowledge-Action.** Chosen from the three stage names. No direct collision found; trademark and domain check pending.
19. **Data sensitivity is the user's responsibility, loudly.** Heavy, front-and-centre warning; expect corporate LLMs; local models as the privacy-safe path.
20. **Apache 2.0 recommended.** Permissive enough for open core; contributors promise not to sue adopters over patents. To confirm.
21. **Sequence: PRD → feedback → prototype → build.** Rather than racing to a working build, validate the journeys with product and engineering contacts first, prototype in Penpot (the open-source Figma alternative), then build with that feedback baked in. The public demo may deliberately use a provider combination different from the J1 example (for example an offline vault and GitHub Issues in place of Confluence and Jira) to prove the agnostic claim. *Amended (v0.9.4):* the build step now starts with the scoped MVP — see entries 28 and 29 and the [MVP ticket breakdown](mvp-tickets.md).
22. **Use the platform's transcript when it exists; summarise per type.** Google Meet and Teams already transcribe, so transcription is a skippable step, not an assumed one — saving cost and a whole LLM call. And one summary prompt cannot serve a stand-up and a refinement session equally, so prompts are per type, fully editable, versioned, and extendable with custom types. Type assignment is by rule, manual choice, or optionally Jev classification.
23. **Vendor API versions are optional capabilities, not core changes.** Providers declare the API version they target and the extra capabilities they offer; the core discovers and uses what is present. New vendor functionality reaches users through a new provider version, never through a change to the core interface.
24. **"Content type" is the general concept; "meeting type" is one family of it.** Captured content is not always a meeting, so the thing that selects a summary prompt cannot be a meeting type. Decision: every captured item gets a content type; meeting types (stand-up, ticket refinement, sprint planning, retrospective as the starting set) and document types are families of content type, with a general fallback. An unclassified item gets the general prompt and a call to action to assign or create a type.
25. **Knowledge and Action are different stages; the knowledge store can be offline.** Confluence and Jira are examples of two different provider categories, not two of a kind: Confluence is a knowledge store, Jira is a work tracker. Decision: rename "documentation provider" to "knowledge provider" so the category mirrors the Knowledge stage (as the work item provider serves the Action stage), and make a local, Obsidian-compatible Markdown vault a first-class knowledge provider alongside Confluence and Notion — plain text with explicit links is the most LLM-readable store there is, and it needs no vendor.
26. **Position against suite lock-in, not bespoke pipelines.** Earlier drafts framed the problem as "everyone rebuilds this pipeline by hand." Feedback: the sharper, truer pain is that the capability is already on sale — but only inside single-vendor suites (Atlassian, Google, Microsoft), at a suite premium, upsold module by module, with cross-provider stacks unsupported. Decision: composability across providers is the stated USP; Section 2, the landing page and the prototype all lead with it. The tagline is "Turn your knowledge into action automatically, with the tools you already know," and the landing page leads with the Capture → Knowledge → Action name itself as the logo rather than a slogan.

*Entries 27 onward come from the MVP scoping sessions of 18 September 2026 and are recorded in v0.9.4. They are grouped loosely: 27–29 set the shape of the build, 30–33 the pipeline, 34–37 the human-facing behaviour, 38–45 the implementation choices, 46–47 the open questions closed, 48–51 the late corrections.*

27. **One persistent core, not serverless.** A reviewer suggested serverless to cut costs. The core is stateful: it holds state across multi-step provider calls, subscribes continuously to the event bus, and coordinates the Outbox retry pattern. Because it must run always-on anyway, splitting it into functions would add network hops and complexity with no cost benefit. Stateless provider calls could go serverless later; the core stays one application.
28. **The MVP is a real slice, not a mock.** Real recording in, real GitHub actions out, dockerised, configured by env vars, with a scripted demo. It is deliberately narrow (one meeting type, three providers, local only) but every piece is production-quality code, not throwaway. The interactive prototype remains the fabricated-data view.
29. **MVP reference providers.** Google Meet (capture), Markdown vault (knowledge), GitHub Issues (work items), plus a real local event bus broker. Chosen to validate the provider interfaces end to end and to prove the agnostic claim with a non-suite combination.
30. **Knowledge and Action communicate only through events.** The Action stage subscribes to "knowledge stored". Jev is not called by the LLM step, so either stage can be swapped or triggered independently.
31. **Capture by polling.** Push notifications need a publicly reachable webhook, which a local run does not have. Polling is simpler and sufficient.
32. **Prompts are versioned SQL data.** They will be configured through the front end, and the audit trail needs to show which version produced which output — neither works if they live in a config file. Keyed by content type; the current version fetched at capture time.
33. **Jev is optional; the decision provider has an LLM fallback.** Most people trying the project will not have a TypeSafe key. The Jev adapter is a thin wrapper calling the TypeSafe API directly, since no Java SDK exists and the LangChain integration is Python. *Amended (v0.9.7):* "no Java SDK exists" should read *no official* Java SDK — see entry 60. The fallback is no longer an independent lookalike either; it ports TypeSafe's own adapter — see entry 59.
34. **Terminal setup for the MVP.** `./setup.sh` (prerequisite checks, credential wizard, writes `.env`) and `./start.sh` (Docker Compose). The user brings their own Google OAuth app; consent runs once and yields a refresh token. The web wizard is deferred.
35. **Triage accept is the final gate.** One clear approval point, not two. Individual accept and reject plus accept all. The demo recording includes a deliberate misclassification so the reject path is shown, and both outcomes are written to the action decision chain.
36. **Failures are visible.** A failed action is a distinct state in the activity log and front end, and is audited. The demo breaks the GitHub token on purpose to show it.
37. **The demo is resettable from the UI.** A front-end button undoes the GitHub actions and repopulates the synthetic data, so the recording can be repeated without terminal work.
38. **Agent workflow conventions.** Ponytail for lean code, Matt Pocock's skills pipeline, strict TDD, minimal hand-picked dependencies (no starter bundle), and an `agents.md` in every folder, so coding agents get local context without inferring intent.
39. **RabbitMQ as the MVP event bus broker.** Simplest of the PRD's candidates (Kafka, RabbitMQ, Google Pub/Sub) to run locally — one container, no coordinator service required.
40. **No audio transcription in the MVP.** Meet always supplies a transcript, so the LLM step only summarises. A capture provider with no transcript is out of scope for now.
41. **Trust-ramp suggestions are in the MVP.** The J5 banners appear once there is enough accept/reject history for an action type, alongside the raw accept/reject data.
42. **GitHub candidate pool is unfiltered for the MVP.** All issues in the configured repo. (What happens to a reference matching no real issue was open when this was decided; entry 49 closes it.)
43. **Outbox depth for the MVP: retry, switch provider, dismiss.** Notification delivery (email/Slack) is deferred; the visible failed state is the notification for now.
44. **The Google OAuth app will be published**, not left in "Testing", so refresh tokens for Drive scopes don't hit the 7-day test-mode expiry.
45. **Front-end hot reload uses polling-based file watching**, the idiomatic approach for a Next.js dev server running against a Docker bind mount, since native filesystem events don't reliably cross that boundary.
46. **Licence confirmed: Apache License 2.0.**
47. **Public demo will be hosted on GCP.**
48. **Jev does mention detection alone.** The LLM step only summarises; it never extracts ticket identifiers. Jev classifies mentions directly from the summarised knowledge content against the real candidate pool, so there is no separate extraction step to keep in sync with it — and no way for extraction to invent an identifier no work item has.
49. **Unmatched mentions are recorded, not dropped.** A reference that doesn't correspond to a real candidate produces no action proposal, but is written to the audit chain and shown in the front end — distinct from a rejected proposal, which was a real, if wrong, match. This closes the question left open in entry 42.
50. **Flyway for SQL migrations, Spring Data JDBC for data access.** Versioned migration files checked into the repo alongside the schema they create; Spring Data JDBC as the query/access layer on top.
51. **The decision layer is built in two passes within one ticket.** First against a stubbed candidate pool and a stubbed LLM fallback, so it's testable standalone; then wired to the real GitHub candidate pool and the real LLM fallback once those land. Splitting it across two tickets would have left a half-built decision layer as a deliverable.

*Entries 52 onward come from the demo-script session of 19 September 2026 and are recorded in v0.9.5. Narrating the product end to end is what surfaced them: each one is a place where saying the pipeline out loud exposed something the written design had glossed over.*

52. **The LLM provider publishes a "content summarised" event; the knowledge provider subscribes to it.** Previously the LLM step handed its output to the knowledge provider directly, which was the one in-process call left in an otherwise event-driven pipeline — and it quietly coupled the two, since the LLM provider had to know a knowledge provider existed. Now every handoff crosses the bus. Either provider can be built, tested and swapped without the other; a test for the LLM provider needs no knowledge store running at all.
53. **The event is named for summarising, not transcribing.** It was first drafted as "content transcribed", but decision 40 removed transcription from the MVP entirely — Meet always supplies a transcript — so an event named after a step that never runs would have been a standing source of confusion, in the code and on camera. Named for what the step actually does.
54. **Low-confidence mentions are proposed, not ignored.** A mention scoring below the threshold used to be dropped. It now becomes a **proposed comment** in the Triage Inbox for a human to confirm. This makes check 1 a three-way outcome — auto-comment, propose, or record as an unmatched mention — and means the Triage Inbox holds two distinct kinds of proposal, which the UI has to keep visually distinguishable. The principle already stated for unmatched mentions ("nothing is silently dropped") did not survive contact with a below-threshold score, and now does.
55. **"Trigger phrase" is the canonical term.** Three terms were in circulation across the PRD, the tickets and the demo narration — trigger phrase, wake word, wake phrase. Standardised on trigger phrase for every identifier, config key and field name, with "wake word" kept only as a plain-language gloss when explaining it to someone new.
56. **The demo script is written before the software.** It doubles as the MVP test plan, so writing it first turns the demo from a thing to be improvised at recording time into a checklist the build has to satisfy. It immediately earned its keep: narrating the pipeline surfaced entries 52 to 55, and comparing the narration against T21's beats showed the reject path and the reset were not being demonstrated at all.

*Entries 57 and 58 come from the MCP session that followed.*

57. **CKA defines an MCP compatibility spec, not a single centralised server — and a deterministic API stays the architectural core.** MCP compatibility is a specification/methodology, published in the repo, covering the whole stack: CKA's own core capabilities and each provider interface. Any component, in the core or built by a third party, can implement it independently; there is no "the CKA MCP server". For the MVP, CKA's own reference implementation follows the spec for the core capabilities only, via the official Spring AI MCP Server Boot Starter, built *after* and *on top of* the deterministic REST API and calling straight through to its existing service methods. The REST API is the ground truth and the MCP layer is the thin wrapper, not the reverse — MCP is still meant to be the primary way an AI agent reaches CKA day to day, but that is a usage goal, not a claim about which layer drives the other's design. The distinction matters because the opposite arrangement would have shaped every application service around tool schemas, making the API a second-class consumer of its own core. Provider interfaces satisfied by an external MCP server are specified for later, not built now. Authentication for the exposed capabilities is still open, since several are mutating.
58. **MCP tool design is held to a discoverability bar.** It isn't enough that an MCP client *can* call CKA's tools — someone who has never heard of CKA, asking their own AI assistant to do something CKA can do, should get it to work with no bespoke integration. Tool names, descriptions and parameter schemas are written and tested so a generic, CKA-naive agent maps a plain natural-language request onto the right tool calls from the exposed schema alone. This is an acceptance criterion on the MCP ticket, not an aspiration.

*Entries 59 and 60 come from a review of TypeSafe's own tooling, recorded in v0.9.7.*

59. **The LLM fallback ports TypeSafe's official adapter rather than imitating Jev independently.** TypeSafe officially publish [`system-one-adapter-python`](https://github.com/typesafe-ai/system-one-adapter-python), a drop-in LLM-backed replacement for their `system_one` evaluation API — official status confirmed by the author, and it is the fact the whole decision rests on: a community-written lookalike would be no more authoritative than ours, so there would be nothing to gain by porting it. Writing our own lookalike would mean owning a shape-matching problem forever: two implementations that must agree on a contract neither of them defines. Porting theirs moves the contract upstream — the response shape, `Noul`/`Score`/`Choice`, corrective retries, probability normalisation and debug/usage reporting all come from the vendor. **Ported to Java rather than run as a Python sidecar:** a sidecar would faithfully reuse their code, but it adds a second runtime, a second place credentials live, and it routes LLM calls outside LangChain4j — which breaks the single-gateway claim in Section 3 and hides those calls from J7 cost tracking. The cost of the port is drift: upstream changes must be tracked by hand.
60. **Community Java SDKs for System One were evaluated and rejected.** Jev shipped on 15 September 2026 and four community Java clients appeared on the 18th and 19th, one advertising a Spring Boot starter. On inspection every one was one to three days old with zero or one star, two were forks of each other, and one carried no licence at all — no grant of rights, which would be indefensible in a repository that ships Apache 2.0 for precisely that reason. Taking a brand-new, unvetted third-party SDK into a Spring Boot app that handles API credentials is a supply-chain risk out of all proportion to the work it saves, and Ponytail favours the thin wrapper regardless. Decision: keep the self-written HTTP wrapper, and re-check when the ecosystem has settled. Note the contrast with entry 59: CKA depends on TypeSafe's Python adapter *because* it is official and therefore authoritative about its own contract, and declines these Java clients *because* they are not. The test is provenance, not language.
